# AeroRadioControl 多端迁移技术评估

## 1. 背景

当前代码库是一个典型的 Android 旧项目，核心能力集中在：

- 登录和 token 刷新
- 巡呼 / 对讲 / 点播 / 任务 / 快捷任务等业务流程
- 后端接口调用和本地缓存
- 录音、TTS、音频播放、扫码、地图、蓝牙、后台服务
- 无障碍自动化、系统权限、设备级控制

目标不是把 Android 代码“原样搬到” iOS 和鸿蒙，而是拆出可复用的业务能力，再分别重建平台层。  
结论先说：这套系统适合做“共享业务内核 + 多端壳层”的迁移，不适合直接做单一代码库全平台复用。

---

## 2. 当前工程判断

### 2.1 现状特征

从工程结构看，当前是标准 Android Studio/Gradle 项目，且存在明显的旧项目特征：

- `app` 是主工程，`screanadaption` 是单独的屏幕适配模块
- 使用了大量 Android 原生能力
- 引入了若干旧版三方库和本地 AAR/JAR
- 依赖较多服务端驱动的业务逻辑

### 2.2 主要技术依赖

当前 Android 侧核心依赖大致分为几类：

- 网络与数据：OkHttp、Gson、RxJava、EventBus
- UI 与列表：RecyclerView、ViewPager、若干旧版适配器
- 音频与语音：`TextToSpeech`、录音、播放、音量控制
- 地图与定位：百度地图 SDK
- 扫码：`simplezxing`
- 设备控制：蓝牙监听、无障碍服务、前台服务、系统级权限
- 历史业务库：`htapplib.aar`

### 2.3 迁移结论

这类项目的迁移关键不在于“页面重画”，而在于“平台能力边界重定义”：

- 业务模型和接口协议大概率可以复用
- Android 特有的系统能力需要替代方案
- 某些能力在 iOS 上只能重构，不能照搬

---

## 3. 迁移目标建议

建议把多端目标拆成三层：

### 3.1 核心层

跨平台共用，优先建设：

- 登录
- token 刷新
- 用户/设备/任务等数据模型
- 后端接口协议
- 本地缓存策略
- 页面业务流程

### 3.2 平台适配层

每个平台单独实现：

- TTS
- 录音和播放
- 扫码
- 定位和地图
- 文件上传
- 权限申请
- 通知和前台保活

### 3.3 平台专有层

只保留在对应平台，或改成交互式替代：

- Android 无障碍自动化
- Android 蓝牙 SCO / 设备广播监听
- Android 系统权限和安装类能力
- 历史厂商 SDK 的平台专用实现

---

## 4. 功能迁移评估

### 4.1 Level 1: 好同步

这部分建议优先做成共享逻辑，尽量一套业务规则，多端复用。

| 功能 | 现状 | 可复用度 | 处理建议 |
|---|---|---:|---|
| 登录 / 鉴权 / token 刷新 | 已有 token 获取和刷新逻辑 | 高 | 抽成统一认证模块 |
| 后端接口调用 | 标准 HTTP 请求封装 | 高 | 保留协议，替换平台网络层 |
| 任务 / 列表 / 表单业务 | 大量页面围绕业务对象展开 | 高 | 提炼为统一业务域模型 |
| 本地缓存 / 偏好设置 | 使用本地存储和数据库 | 高 | 抽象存储接口，平台分别落地 |
| 业务状态流转 | 事件驱动较明显 | 高 | 改成统一状态管理层 |

### 4.2 Level 2: 中等难度

这部分能做，但需要平台能力适配，通常需要单独验证。

| 功能 | 现状 | 可复用度 | 处理建议 |
|---|---|---:|---|
| TTS | Android `TextToSpeech` | 中 | 抽象语音服务，平台实现各自引擎 |
| 录音 / 播放 / 音量控制 | 依赖 Android 音频栈 | 中 | 设计统一音频控制接口 |
| 文件上传 / 重新上传 | 服务型上传逻辑 | 中 | 网络层可共用，文件选择和权限要平台化 |
| 扫码 | Android 扫码 Activity | 中 | 改成统一扫码组件，平台使用各自 SDK |
| 地图 / 定位 | 百度地图 | 中 | 重新评估是否继续依赖百度，或平台替换 |
| 前台通知 | Android NotificationChannel | 中 | iOS / 鸿蒙分别实现通知和常驻策略 |

### 4.3 Level 3: 同步困难

这部分不是简单移植，而是要明确“保留、替代、删除”三选一。

| 功能 | 现状 | 同步难度 | 处理建议 |
|---|---|---:|---|
| 无障碍自动化 | 自动点击安装/确认按钮 | 高 | iOS 基本不可照搬，建议重构流程 |
| 后台常驻服务 | 多个 Service 长驻运行 | 高 | 改成平台允许的后台机制 |
| 蓝牙 SCO 切换 | 监听蓝牙并切换音频链路 | 高 | 需按平台重新设计音频链路 |
| 系统级权限 | 全盘存储、安装包、系统设置类权限 | 高 | 必须收敛为标准应用权限 |
| 历史 Android 专有库 | `htapplib.aar`、旧 JAR | 高 | 必须确认是否存在 iOS / 鸿蒙对等 SDK |

## 5. 推荐技术架构

### 5.1 总体结构

建议按下面的方式拆分：

```text
业务域层
  - 登录
  - 任务
  - 对讲
  - 点播
  - 巡呼
  - 录音/播报

平台抽象层
  - 网络
  - 存储
  - 语音
  - 音频
  - 扫码
  - 地图
  - 权限
  - 通知

平台实现层
  - Android
  - iOS
  - 鸿蒙
```

### 5.2 建议的复用边界

可共享：

- 接口定义
- DTO / Model
- 校验规则
- 任务状态机
- 业务流程编排
- 错误码和统一提示文案

不共享：

- 页面容器
- 权限申请
- 系统通知
- 后台服务
- 蓝牙、定位、扫码等原生入口

### 5.3 推荐做法

如果项目最终要持续维护三端，建议优先做：

1. 业务协议和数据模型统一
2. 平台能力接口统一
3. UI 页面分端实现
4. 关键硬件能力走平台适配

---

## 6. 现有 Android 项目的重构建议

### 6.1 先抽业务内核

建议先从现有工程里抽出以下部分：

- 网络请求封装
- token 管理
- 业务 model
- 任务状态和事件定义
- 本地缓存接口
- 文件传输协议

### 6.2 再隔离平台能力

把下面这些能力从业务代码里剥离出去：

- TTS
- 录音
- 播放
- 扫码
- 地图
- 定位
- 蓝牙
- 通知
- 权限
- 文件访问

### 6.3 最后做平台实现

分别建立：

- Android 实现
- iOS 实现
- 鸿蒙实现

这样后续即使某个平台能力变化，也不会反向污染业务代码。

## 7. 分阶段迁移方案

### Phase 0: 需求冻结

输出结果：

- 必须保留的功能列表
- 可以降级的功能列表
- 只保留 Android 的功能列表
- iOS / 鸿蒙首发范围

### Phase 1: 业务内核拆分

输出结果：

- 统一接口定义
- 统一数据模型
- 统一状态流转
- 统一错误码

### Phase 2: 平台抽象定义

输出结果：

- 网络接口
- 存储接口
- 语音接口
- 播放接口
- 扫码接口
- 地图接口
- 权限接口
- 通知接口

### Phase 3: Android 先重构

输出结果：

- 先把 Android 改成“业务内核 + 平台实现”
- 去掉业务层对系统能力的直接依赖
- 保留现网可运行能力

### Phase 4: iOS / 鸿蒙接入

输出结果：

- 按统一协议实现平台能力
- 逐个补齐页面
- 分功能验证

## 8. 研发风险点

### 8.1 高风险

- `htapplib.aar` 是否有跨平台版本不明确
- 无障碍自动化在 iOS 上基本不可等价实现
- Android 后台服务模式不能直接迁移
- 百度地图能力需要重新验证是否保留

### 8.2 中风险

- 旧版第三方库兼容性差
- 现有项目命名和结构较旧，重构成本高
- 业务散落在大量 Activity / Fragment 中，拆分工作量大

### 8.3 低风险

- 接口层、数据层、token 机制、缓存机制可以较稳地复用
- 大部分表单和列表逻辑可以通过统一业务层迁移

---

## 9. 产品和研发需要同步确认的问题

1. iOS / 鸿蒙是做“核心业务版”，还是做“尽量一致版”？
2. 巡呼、对讲、点播、任务、快捷任务里，哪些是首发必须项？
3. TTS、录音、播放、扫码、地图，哪些是必须保留能力？
4. 蓝牙、无障碍、后台常驻，哪些必须保留，哪些可以替代？
5. `htapplib.aar` 是否是核心控制库？是否有 iOS / 鸿蒙对等 SDK？
6. 目标分发方式是什么？
   - App Store / 鸿蒙应用市场
   - 企业内部分发
   - 测试验证包
7. 后端接口是否保持不变？
8. 是否允许 Android 特有流程在 iOS / 鸿蒙改成交互式替代方案？

---

## 10. 推荐结论

如果目标是尽快推进三端落地，建议采用下面的策略：

- **先统一业务内核**
- **再拆平台能力**
- **Android 先重构成参考实现**
- **iOS / 鸿蒙按平台单独实现**

不要一开始追求“三端完全同构”，否则会被 Android 专有能力拖住，整体周期会明显放大。
